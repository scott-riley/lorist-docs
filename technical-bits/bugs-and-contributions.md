# Bugs and contributions

Lorist is an open source project, but might be a little different to the open source projects that you’re used to. Namely, feature contributions are actively discouraged. That stuff gets worked on behind the scenes, and it’s _highly unlikely_ that feature suggestions will be accepted.

Similarly, issue reports that read like ‘this thing is supported in X/Y/Z but not here’ will likely be disregarded, unless it’s something mega like missing an absolutely key part of Markdown.

::: info {no-title}
**TL;DR** – if you’re building or suggesting features, prepare to be disappointed. If you’re fixing bugs, prepare to be adored.
:::

## Raising issues

If you’re experiencing an issue with Lorist that is preventing you from using or enjoying it, you can raise an issue in the <a href="https://github.com/scott-riley/lorist-writer/issues">Issues section of the GitHub repository</a>.

When raising an issue, include screenshots, a description of the problem, what you were doing at the time, and anything specific about your folder/document that might help diagnose. If you’re capable of deeper diagnostics like checking console logs and other Dev Tools magic, that’s also much appreciated.

## Contributing

If you want to contribute to Lorist, firstly, amazing, more people should give open source projects some love. Secondly, you might want to reconsider unless you _really_ love fixing bugs. As stated above, feature contributions are actively discouraged. This is for a number of reasons.

Primarily, Lorist is an opinionated product, and as such has a very high threshold for what kind of feature makes it into the product. A lot of discovery and contemplation goes into every feature, and more features have been removed from Lorist than added. We are, at launch, in a feature deficit compared to the first iteration.

If you find yourself thinking ‘wow, Lorist really needs this thing’ then you are encouraged to ask ‘why?’—and share that why! An issue that reads more like ‘I was using it to do this thing, and I really wished it had X, because Y, and that would allow me to Z’ is extremely valuable and basically free user testing. But asking for X feature (or even worse spending your valuable time coding it) directly is likely a waste of your time.

Secondly, it’s so easy now to throw a codebase at an LLM and say ‘make it do this!’ and then feel like you’ve achieved something and then submit a PR to an open source repo with a single maintainer who then has to review AI–generated code without getting an aneurysm. Lorist literally exists because every other app I was using was just becoming a dumping ground for random, incessant features now that the floodgates have opened to vast quantities of ‘this might be a good idea’ features completely devoid of forethought.

It makes me sad that this is the state we’re in, but I’ve seen it enough to want to get ahead of that.

Having said all of that, if you’ve read all this and still think _wow, I’d sure love to fix a real bug in this little open source product_ and you do spot an accepted issue that you think you can fix, then you are truly the best of us. Bugfixes are accepted with open arms.
